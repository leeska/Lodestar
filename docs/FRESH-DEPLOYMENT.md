# 新部署与数据兼容

当前 Lodestar 使用按模块编号的 SQLite 迁移。v2.0.0（原 schema 30）及后续版本的数据目录可以原地升级；更早的数据需要使用新目录部署。2026-11-09 曾采用「仅支持全新部署」的阶段性基线，已被当前迁移机制取代。

具体安装与改名步骤见 [DEPLOYMENT.md](DEPLOYMENT.md)，迁移机制见 [ARCHITECTURE.md](ARCHITECTURE.md#数据库迁移)。

## 全新部署

- 使用新的私有数据目录，数据库名为 `lodestar.db`。
- Server 按 `cmd/server` 的 `shippedModules()` 顺序执行核心与模块迁移，每条迁移在独立事务中执行，并记录到 `schema_migrations`。
- 初始化成功后，`PRAGMA user_version` 为 31；实际结构版本由各模块的迁移记录决定，不靠继续增加这个值表示每次发版。
- 初始化或迁移失败时，不把失败的迁移记为已完成；修复后可重试。
- `vault.key` 在数据目录首次生成，用于资产敏感字段加密。备份或恢复整个实例时必须保留这份密钥。

## 可以原地升级的数据

| 起点 | 当前处理 |
| --- | --- |
| v2.0.0 数据库，`user_version = 30` | 记为核心基线迁移已完成，再执行后续核心与业务模块迁移 |
| 迁移管理的数据库，`user_version = 31` | 根据 `schema_migrations` 补上本二进制中尚未执行的迁移 |
| 改名前的 `tza-probe.db` | 数据目录内不存在 `lodestar.db` 时，Server 自动接纳旧文件名及其 WAL、共享内存文件；服务、用户与目录的迁移由安装脚本负责 |

新增迁移只能追加，不能改写已经上线的迁移。数据库中本二进制认识的模块若存在更新的迁移版本，会拒绝打开；只有数据库里存在、本二进制未包含的模块不作为拒绝理由。

## 必须使用新目录的情况

- 早于 v2.0.0 的 schema，或只留下 `tza-v2.db` 的旧目录。
- 无版本标记但已有业务表的非空数据库。
- 损坏或与当前数据库格式不符的数据，不能靠修改 `user_version` 绕过检查。

新部署不清空或覆盖旧库，也不自动接管历史独立 IPSentinel 安装器。旧服务、凭据与数据需由运维另行备份、处理。

## 升级、备份与回滚

1. 使用新二进制执行 `lodestar check-data --data <数据目录>`，只读检查能否升级；发布包安装脚本也会先做这项检查。
2. 涉及数据库迁移时，停服务并备份整个数据目录，包含数据库、保险箱密钥、账号、主题、插件与其他状态。
3. 先升级 Server，再升级节点 Agent；改名前的安装使用 [改名迁移流程](DEPLOYMENT.md#从-tza-改名为-lodestarv300)。
4. 回滚时恢复旧二进制和升级前的数据目录。旧二进制可能拒绝更新的迁移记录；v2.0.0 也会拒绝 `user_version = 31`。

Agent 升级仍须使用可信签名密钥，历史失密的信任根不能恢复。主控的加密备份与节点存放位置需要管理员配置，存在备份模块不等于已经完成异地备份。

## 验证

`internal/storage/migrate_test.go` 覆盖 v2.0.0 原地升级、重复启动不重跑迁移、失败回滚与重试、更新版本拒绝和迁移顺序校验。`schema_test.go` 覆盖不支持的数据保留、初始化回滚、新库结构和升级前检查；`backup_test.go` 验证在线数据库快照能独立重开。

这些是测试覆盖范围，不表示本次已经运行检查或完成线上验收。完整验证方法见 [VERIFICATION.md](VERIFICATION.md)。
